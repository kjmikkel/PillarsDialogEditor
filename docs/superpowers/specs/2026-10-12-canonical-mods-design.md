# Canonical mods — design

GitHub issue [#138](https://github.com/kjmikkel/PillarsDialogEditor/issues/138). Follows #122
(canonical conversations). Approved in brainstorming on 2026-10-12.

## Goal

#122 proves the editor *reads* each game's canonical conversation and that an unchanged save keeps it
intact. Nothing proves that what the editor *writes* — new nodes, links, conditions, scripts, text,
VO — is valid. The save-fidelity bugs #111–#116 and the recent #139/#141 were all of that kind.

A **canonical mod** per game closes the gap: a Dialog Editor project plus its `.dialogpack`, checked
in, that touches as much of what the editor can write as possible, then gets applied through every
delivery path and verified.

## Decisions

| Question | Decision |
|---|---|
| How the mod is authored | **Generated by editor code.** A test-side scenario drives the real view models; the output is checked in as golden files and regenerated on demand. |
| Delivery | **Three PRs.** PR 1: harness + PoE2 mod + automated tests. PR 2: PoE1 mod + `OEIFormats` check. PR 3: in-game checklist, then run once per game. |
| Bugs the mod exposes | **File and skip.** File an issue, mark the one failing check `Skip = "#NNN"`; each fix is its own red/green PR that removes the skip. |
| Harness shape | **Scenario builder in the test project + golden files** (not a separate tool, not in-memory only). |

## 1. Layout and components

```
DialogEditor.Tests/
  CanonicalMod/
    CanonicalModScenario.cs      the scripted edits, one method per feature group
    CanonicalModBuilder.cs       runs a scenario against a fake install → project + pack
    CanonicalModGoldenTests.cs   rebuild == checked-in; env var regenerates
    CanonicalModApplyTests.cs    apply via each delivery path, then verify
    CanonicalModVerifier.cs      shared post-apply checks
  Fixtures/CanonicalMod/
    README.md                    feature → where the mod uses it (conversation, node id)
    poe2/canonical_mod.dialogproject, poe2/_vo/…, poe2/canonical_mod.dialogpack
    poe1/…                       (PR 2)
```

- **`CanonicalModScenario`** — per-game edit scripts written against a thin facade over the real
  view models (`MainWindowViewModel`, `ConversationViewModel`, `NodeDetailViewModel`,
  `ConditionEditorViewModel`). Each step carries a feature tag (e.g. `[Covers("links.weight")]`).
  A test asserts the tags and the README's feature rows match exactly, both ways, so they cannot
  drift apart.
- **`CanonicalModBuilder`** — copies `Fixtures/Canonical/<game>` to a temp folder, creates a project
  the way *New Project* does, runs the scenario, saves through `SaveProject` (the GUI's own
  diff-to-patch path), then builds the pack with `VoPackExporter.ExportAsync`. VO import goes through
  the real `IVoImporter` path; the `.wem` inputs are invented placeholder bytes.
- **Determinism** — fixed node ids where the editor lets the caller choose, fixed annotation text, no
  clock, no random GUIDs. Anything nondeterministic that leaks into the output fails the golden test.
- **Content** — all text, GUIDs, variable names and VO bytes are invented, in the style of #122
  (`c0a1c0a1-…-000000000122`). The repository is public.

## 2. What the PoE2 mod contains

**A. Edits to `canonical`** (node ids from `Fixtures/Canonical/README.md`):

| Feature group | Edit |
|---|---|
| Nodes — add | New NPC line 11 after 10; new player choice 12 under 0; new script node 13 |
| Nodes — convert / delete | Convert player 3 → NPC line; delete node 9 (bank 5 keeps child 8) |
| Kept types | Edit bank 5 (add new child 14) and trigger 6 (re-point its start node); node −200 untouched |
| Links | Add 0→12 and 10→11; remove 2→5; re-weight 0→2 to 3; all three QuestionNodeTextDisplay values; change link 1→4's conditions |
| Conditions | On a node and on a link: nested AND/OR, negation, a multi-parameter call; clear one condition entirely |
| Scripts | Add OnEnter/OnExit/OnUpdate on 13; edit node 4's per-script conditional (#115); remove one script |
| Properties | Every DisplayType and Persistence value across new/edited nodes (#114); speaker and listener change; comments; HideSpeaker on and off |
| Text | Edit node 0 text and female variant; new text with a token and `<i>` markup; a `de` translation for new and edited nodes |
| VO | Import a placeholder `.wem` for node 11 (HasVO); ExternalVO alias on node 12 → node 7's file; turn one HasVO off |

**B. New conversation `canonical_mod_new`**, made with the editor's New Conversation command: NPC →
two player choices → end, text in `en` and `de`, one conditioned choice. It is listed in
`NewConversations`, so the patcher has to *create* its files.

**Out of scope:** Bark preview, annotations and layouts (editor-only metadata, never in game files —
left as the edits produce them); spell-check dictionaries (not part of a mod).

**PoE1 (PR 2)** mirrors section A and B minus what PoE1 lacks (link conditions, per-script
conditions, `.wem` VO) and adds a `VOFilename` edit. Its link edits go through the PR 1 harness
unchanged; PoE1-only expectations (e.g. no `<Conditionals>` added to links, #141) live in its
verifier.

## 3. Verification per delivery path

Each `CanonicalModApplyTests` case starts from a fresh `FakePoe2Game.Canonical()` copy, applies the
**checked-in** `.dialogpack`, and runs `CanonicalModVerifier`:

1. **`dialog-patcher`** — `PatcherCommand` in-process with `<fake-root> canonical_mod.dialogpack`
   (argument parsing and pack extraction included).
2. **Patch Manager** — `PatchManagerViewModel`, pack added as an entry, `ApplyCommand`.
3. **Test Patch (F5)** — `MainWindowViewModel` with the generated project open, `TestPatchCommand`
   (the separate `DoTestPatch` route).

`CanonicalModVerifier` checks:

- **Editor model** — reload with the editor's own provider; every scenario step has its own
  expectation (node 11 exists with this text, link 0→2 has weight 3, the condition tree on 1→4 is
  exactly this, …). One assertion per README feature row, so a failure names the feature.
- **The three paths agree** — the written game files are byte-identical across all three paths.
- **Untouched stays untouched** — node −200, and conversations and stringtables the mod does not
  touch, are byte-identical to the fixture.
- **PoE2 property check (#116)** — every written node carries only the properties its `$type`
  declares in OEIFormats. The allowed-property table is derived from the decompiled model once and
  checked in (property names only, no game data).
- **VO** — each `.wem` lands where the game resolves it; the ExternalVO alias points at an existing
  file.
- **Reversibility** — *Remove all mods* (patcher paths) and *Restore Conversation* (F6, Test Patch
  path) return the fake install to the fixture's exact bytes, including removing
  `canonical_mod_new`'s files.

**Game model (opt-in, `Category=GameData`, like #117)** — PR 2 runs the applied PoE1 files through
the install's own `OEIFormats` `XmlSerializer`, as the #139 test does. For PoE2 the #116 property
check is the guard.

A failing check gets `Skip = "#NNN"` and a filed issue (search existing issues first).

## 4. Golden files, checklist, delivery

**Golden files.** `CanonicalModGoldenTests` builds the mod into a temp folder and compares it with the
checked-in copy: the project JSON exactly; the pack by entry list and per-entry bytes (`FORMAT.md`
included), ignoring zip metadata such as timestamps. On a mismatch it names the first differing entry
and line, and says to rerun with `DIALOGEDITOR_REGENERATE_CANONICAL_MOD=1` if the change was
intended. That run rewrites the files **and still fails**, so a regeneration can never pass silently
in CI. A regenerated mod is an ordinary reviewable diff.

**In-game checklist** (`docs/canonical-mod-checklist.md`, PR 3):

- Back up / verify the game; install the pack with the standalone patcher.
- Reach the content through the game console. Neither game has a dedicated conversation command,
  but the console resolves script functions (`CommandLineRun` searches `Scripts` as well as
  `CommandLine`) and accepts the special object name `oei_player`:
  - PoE2: `StartConversation oei_player <conversation> 0`
  - PoE1: `StartConversationFacingListener oei_player <conversation> 0`

  Verified from the decompiled code; the first in-game run confirms the exact argument form and
  whether cheats (`iroll20s`) must be on, and the checklist is corrected if needed. The mod's NPC
  speaker GUID is invented and not in the world; the first run also records how the game presents a
  conversation whose speaker is absent.
- One checkbox per README feature row, in play order, each saying what you should see.
- Check the game's output log for conversation errors.
- A results table (date, game build, pass/fail) filled in once per game; failures filed as issues.
- Clean-up: *Remove all mods*, then verify the game files.

**Delivery.**

- **PR 1** — harness, PoE2 mod, golden and apply tests, `Fixtures/CanonicalMod/README.md`. Also
  refreshes the canonical README's stale *Known gaps* list (#139 and #141 are fixed).
- **PR 2** — PoE1 mod, PoE1 verifier expectations, opt-in `OEIFormats` check.
- **PR 3** — the checklist; then the in-game run per game, results recorded in the doc.

## Done when

- Both canonical mods are checked in with a README mapping each feature to where the mod uses it.
- The golden and apply tests are green, or skipped against the specific open issue each exposes.
- The in-game checklist exists and has been run once per game, with failures filed.
