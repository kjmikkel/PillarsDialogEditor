## 2. Summary
The editor is in good shape for a mouse user who already knows it. The tooltip, UIA-name and contrast ratchets cover a lot, and the canvas has real keyboard navigation. It fails its two primary audiences in specific places:
- A Reader without a project can edit text by accident (F-4).
- A keyboard or screen-reader Reader cannot follow a conversation: the canvas has unnamed, invisible tab stops and node selection is never announced (F-5, F-6).
- Esc closes almost none of the app's windows (F-32, F-33). On the crash-recovery dialog the code maps Esc to Discard, which deletes the recovery copy (F-34, seen in code).

The Patcher and CLI work for a careful Player. A typo'd `--dryrun` installs for real (F-44), and the GUI reports success even when a mod matched nothing (F-40).

Top problems:
- **F-4**: a "Viewing only" Reader can edit node text and gets a dirty marker.
- **F-34**: Esc on Autosave restore deletes the only copy of crashed work.
- **F-5 / F-6**: the canvas is not usable with a screen reader or by Tab.
- **F-44**: unknown CLI flags are ignored, so a dry-run typo modifies the game.
- **F-40**: Patch Manager says "Applied N patches" when a mod matched no conversation or a list entry was skipped.

Keep:
- Canvas keyboard navigation by graph relation: arrows move to child, parent and sibling, Home goes to the root, Enter goes to the details (but see F-4), and Shift+F10 opens the menu. The keys are handled by the canvas view (`ConversationView.axaml.cs:109-145`), not by the focused port, so the fixes for F-5 and F-6 can keep them. Add naming and visible focus on top; don't replace them.
- Node type is shown by shape glyph plus colour plus label, and connection type by dash pattern with a legend. Other places that pair colour with text or a glyph:
  - the "●" edited marker in the tree
  - W8's Added/Changed/Removed swatches with labels
  - W15's "× Missing"
  - W7's "Never checked"

  COLOR-1 holds in these, including the colour-blind palette (F-41, in the Patcher, is an exception).
- Wording that already answers the user's real question:
  - the "Viewing only" status line
  - D1's message ("…game files are not touched until you run Test Patch (F5)") and its verb buttons (Save to Project / Discard Changes / Stay Here). Its Esc handling is a separate problem (F-33).
  - W13's empty state ("Add mods (.dialogpack files) above…"), which is the model for F-25
- The existing ratchets:
  - `AutomationNameTests`, `AutomationHelpTextTests`, `InputControlTooltipTests`
  - `PaletteContrastTests`, `ListSelectionContrastTests`
  - `NoHardcodedUiStrings*`
- The Player's undo path (`--restore` and Remove all mods), documented CLI exit codes, and the refusal of newer formats before anything changes.

## 4. Standards

### A11Y-1: Text contrast at least 4.5:1 (3:1 for large text)
Rule: Text and images of text have a contrast ratio of at least 4.5:1 against their background; large text (≥18pt regular / ≥14pt bold, ≈24px / ≈18.5px) at least 3:1. Disabled controls are exempt.
Source: https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html
Status: researched 2026-10-24
Note: `PaletteContrastTests` tests `Brush.Text.Muted` against the 3:1 non-text ratio, although the app uses it for text, which needs 4.5:1. See F-11.

### A11Y-2: Non-text contrast at least 3:1
Rule: Visual information needed to identify a control, its state, and the keyboard focus indicator has at least 3:1 contrast against adjacent colours.
Source: https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html
Status: researched 2026-10-24

### A11Y-3: Every control exposes a name and role
Rule: For every UI component the name and role can be programmatically determined, and states and values the user can set are exposed to assistive technology.
Source: https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html ; project rule CLAUDE.md "UI Automation Support"
Status: researched 2026-10-24

### A11Y-4: All functionality operable from the keyboard
Rule: Everything that can be done with a pointer can be done from the keyboard; controls are reachable by Tab and invokable with Enter/Space.
Source: https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html ; https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility
Status: researched 2026-10-24

### A11Y-5: Visible keyboard focus
Rule: Any keyboard-operable UI has a mode in which the focus indicator is visible.
Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html
Status: researched 2026-10-24

### A11Y-6: Focus order preserves meaning
Rule: Focus moves through controls in an order that preserves meaning and operability (generally the visual reading order).
Source: https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
Status: researched 2026-10-24

### LAYOUT-1: Text resizes to 200% without loss of content or function
Rule: At 200% text size (and steps between), no text or control is clipped, truncated, overlapped or hidden without a way to reach it.
Source: https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html
Status: researched 2026-10-24

### COLOR-1: Colour is not the only means of conveying information
Rule: Colour is never the sole visual cue for information, state or an action.
Source: https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html
Status: researched 2026-10-24

### NAV-1: F6 cycles between major panes
Rule: F6 / Shift+F6 move focus between the window's major regions (docks), each with an accessible name. F6 is a platform convention for pane navigation.
Source: https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility
Status: researched 2026-10-24

### CONTENT-1: Empty states explain themselves
Rule: An empty area says why it is empty (not loaded, nothing matches, nothing yet), what goes there, and how to fill it.
Source: https://www.nngroup.com/articles/empty-state-interface-design/
Status: researched 2026-10-24

### CONTENT-2: Consistent terms and figures
Rule: The same thing is called and counted the same way everywhere.
Source: https://www.nngroup.com/articles/ten-usability-heuristics/ (#4 Consistency and standards)
Status: researched 2026-10-24

### CONTENT-3: Speak the user's language
Rule: Show words and concepts familiar to the user rather than internal names or raw values, unless the audience needs the raw value (then explain it).
Source: https://www.nngroup.com/articles/ten-usability-heuristics/ (#2 Match between the system and the real world); docs/audience.md:33-35 (Curious: raw values visible and explained)
Status: researched 2026-10-24

### CONTENT-4: Every interactive control has a descriptive tooltip
Rule: Every interactive control carries a detailed ToolTip explaining its purpose and effect; only controls whose label is fully self-explanatory in context (OK/Cancel) are exempt.
Source: CLAUDE.md "UI/UX Guidelines" (project spec)
Status: researched 2026-10-24

### FEEDBACK-1: Errors are specific and constructive
Rule: Error messages name the specific problem in plain language and suggest a way forward; they don't flood the user.
Source: https://www.nngroup.com/articles/error-message-guidelines/
Status: researched 2026-10-24

### FEEDBACK-2: Prevent errors before they happen
Rule: Design out slips with constraints and confirmations, especially before destructive or hard-to-undo actions.
Source: https://www.nngroup.com/articles/ten-usability-heuristics/ (#5 Error prevention)
Status: researched 2026-10-24

### FEEDBACK-3: Reader can't change game files or work by accident
Rule: A Reader must never be able to change a game file, or their own work, by accident; nothing a Reader needs may require knowing how editing, projects or diffs work.
Source: docs/audience.md:52-54
Status: researched 2026-10-24

### FORM-1: Dialog buttons name the action; safe Esc dismiss
Rule: Dialog buttons use specific verbs that answer the main instruction; every dialog has a safe dismiss action reachable with Esc.
Source: https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/dialogs-and-flyouts/dialogs
Status: researched 2026-10-24

### CLI-1: Validate input and bail out before anything happens
Rule: A CLI validates its arguments (including unknown flags) and stops with an understandable error before doing anything; it suggests the likely intended flag when it can.
Source: https://clig.dev/ (Robustness: "Validate user input"; Help: "suggest it")
Status: researched 2026-10-24

### CLI-2: Concise help on a usage error
Rule: When required arguments are missing, show concise help (description, one or two examples, pointer to --help), not the full help.
Source: https://clig.dev/ (Help: "Display concise help text by default")
Status: researched 2026-10-24

### CLI-3: Options do what the help text says
Rule: Each option behaves as its own `--help` text describes.
Source: DialogEditor.PatchCli/PatcherCommand.cs:22-63 (the CLI's help text is its spec)
Status: researched 2026-10-24

## 5. Findings

Evidence paths starting `shots/` are under `docs/ui-ux/reports/2026-10-24-whole-app/`. Code paths are under `DialogEditor.Avalonia/` unless they say otherwise.

How the impact anchor is applied to accessibility: **high** when the defect stops a keyboard or screen-reader user from completing a primary flow (FL1–FL3, FL5, FL6), or leaves them unable to tell where they are (focus invisible, or nothing announced); **medium** when the flow can be completed but is slowed or the information is hidden; **low** when text is only marginally below its ratio or the task is a rare one. Outside accessibility, a defect that can destroy the user's work or change game files by accident counts as blocking the task, so it is also **high**. "Also breaks" lists other standards, and may also name the flows (FL-n) a finding affects.
